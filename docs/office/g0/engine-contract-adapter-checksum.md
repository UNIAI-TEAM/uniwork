# DOC-004 task 4.4 - real-engine output checksum harness (UNI-668)

`scripts/office-g0/engine-contract-adapter-checksum.mjs` records real-engine
output-checksum evidence for DOC-004 task 4.4. This is bounded checksum evidence;
full DOC-004 task 4.4 and G0 acceptance remain with the Advisor. The output-checksum rule
previously had only MODELED (`reference_test`) evidence, and the real-adapter
harness did not feed real engine output through the boundary. This harness drives
the REAL pinned DOCX engine host, takes the ACTUAL generated bytes and the checksum
the engine reported, and runs that real result through the revised reference boundary.

It does not replace real engine execution, and it does not duplicate the boundary's
checksum rule: the boundary itself recomputes SHA-256 over the actual bytes and
compares the declared value.

## The named fault seam

    installed at: producer engine result.declared_checksum
    appears AFTER the real POST /engine/docx-edit produced its artifact
    the real bytes are NEVER altered by this harness

The reference boundary validates a job through `createBoundary(...).run(job)` and
calls the injected engine **synchronously**. A loopback HTTP call is asynchronous,
so the harness first captures the real engine result once, then hands the boundary
a synchronous engine closed over that captured result. The only difference between
the accepted and the refused path is the DECLARED output checksum:

- `checksum_ok`: `declared_checksum` is the checksum the ENGINE reported
  (`result.persistedHash`) for the artifact it persisted.
- `checksum_tamper`: `declared_checksum` is `tamperDigest(engine-reported)` - the
  first hex nibble flipped, so it is a 64-hex value the engine never reported. The
  bytes passed to the boundary are byte-identical.

## How to run

    <pinned node> scripts/office-g0/engine-contract-adapter-checksum.mjs \
      --work   <fresh dir under the shared .uniwork-dev> \
      --source <prepared source tree> \
      --node   <pinned node executable> \
      --engine-port <a free port> \
      --fixtures-source <dir holding g0-kitchen-sink.docx> \
      [--print]

The harness boots the real host from its own lab, stops it, and proves the owned
port is released. Before creating any directory it applies the SAME fresh-work
containment the frozen launcher uses (`assertWorkInsideWorkspace`): `--work` must
sit inside the shared `.uniwork-dev` and overlap neither the pinned source, this
checkout, the shared `office-g0` tree, the pinned tools tree, nor the sibling
worktrees. Exit 0 only when every literal check passes and cleanup is proven. A
non-zero exit never means "clean".

## What the run proves (two paths, literal assertions)

Path 1 - untampered real-engine output is ACCEPTED:

- the artifact's real bytes hash (independently computed) equals the checksum the
  engine reported and the checksum the boundary runs on;
- the boundary commits exactly ONE version whose stored bytes hash to that
  checksum, with the real output length.

Path 2 - only the declared checksum is altered AFTER real engine output:

- the boundary returns exactly
  `engine_checksum_mismatch`, `status 502`, `error_class engine`,
  `kind output_checksum`, `retryable true`, `fidelity_preserved true`;
- ZERO store puts and ZERO version commits, no ledger row, and the current
  revision and version pointer are unchanged;
- the original fixture and the previously accepted good output remain
  byte-identical.

## Negative controls

- an unreachable engine host FAILS; a missing/absent fixture FAILS - neither is
  ever a pass;
- the refusal oracle is non-vacuous: an ACCEPTED job satisfies NONE of the refusal
  assertions, and a non-checksum refusal (`engine_crashed`,
  `engine_unavailable`) does NOT count as the target result;
- the "both paths used the SAME capture" claim is MEASURED from the bytes each
  captured engine actually served (`single_capture_used_for_both_paths` compares
  the two served-byte hashes), never a hardcoded true;
- writable-path containment refuses lexical traversal and an escaping junction.
  The probe creates a unique directory with an owner marker and deletes only that
  owned directory. A pre-existing sibling, including `uni668-escape-target`, is
  not adopted and not removed. `containment.escape_target_removed` means this
  invocation's owned target is gone. `containment.owned_resources_absent` means
  the owned link directory and junction are gone too.

## What is real, what is a controlled fault, what is modeled

- REAL: the DOC-003 engine host (`e2e/office-g0/engine-host.mts`), the loopback
  HTTP transport, the DOCX route, and the artifact bytes on disk.
- CONTROLLED FAULT: the single declared output-checksum field. A controlled fault is
  not a spontaneously occurring engine defect.
- MODELED: the reference boundary's auth/grant, object storage and version commit
  (`engine-contract.mjs`'s own in-memory fakes).

This is NOT the Go service, NOT production object storage or commit durability, NOT
product auth/ACL/tenant isolation, and NOT deployed fault coverage. It makes no
offline/self-contained package claim. It does not change the DOC-004 register row
or claim all task-4.4 gates complete; the Advisor decides whether and how a
canonical row can use this evidence.

## Checksum order for this revision

`engine-contract.mjs` hashes a private copy of the produced bytes and compares
`declared_checksum` before any ledger row, `store.put`, or `commitVersion`. A
mismatch records zero puts and zero commits. Declared length uses that same
pre-storage check. A commit failure after a successful put still leaves an orphan.
The original zero-storage and zero-commit criterion is **MET** for this revision.
Earlier evidence that recorded one staged put is a previous revision and is not
relabeled.

## Changed boundary and unchanged dependencies

This revision changes `engine-contract.mjs`, its boundary tests, the checksum
harness, its focused tests and this document. The checksum and declared-length
checks now precede ledger and object storage. Direct counters pin zero ledger,
put and commit attempts; the refusal oracle also checks no object/key and an
unchanged version pointer. A refused attempt still consumes its grant and
replays the same terminal result without another write.

`engine-contract-adapter.mjs` and its 11 case oracles, the launcher and its tests,
the e2e engine modules, shared source, source manifest, register and ADR remain
read-only inputs. Historical one-put reports retain their original results.

## Limitations

- Windows-only process evidence; no Unix process-tree proof.
- Cleanup uses a forced `taskkill /T /F` on an owned PID; an external forced kill of
  the launcher PID can still orphan descendants (a named G0 limitation).
- The toolchain bytes are observed, not byte-pinned.
- Reported disk digests use an independently computed `crypto.createHash("sha256")`,
  not the boundary's own `sha256Bytes` helper, so a reported digest is never
  verified with the same helper that validates it.
- The prepared dependency cache is an authorized input; offline vendoring is out of
  scope.
- The frozen launcher test file hardcodes ports 5397-5406 (not changed here).
