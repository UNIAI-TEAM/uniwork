# A-part-slides — fork `apps/slides` shortcut inventory

Fork @ `d999b8801` (read-only). 119 rows in `A-part-slides.csv`. Surface convention: the Electron renderer code is also what runs inside the web frame, so renderer rows are `web-frame`; main-process menu accelerators are `desktop-shell`; `web/modules/slides` + `web/docs/bridge` rows are `web-frame` (bridge code that runs in the frame page). `ime_safe`: `yes` = checks `isComposing`/229; `no` = plain-key (Enter/Esc/Tab/typing) handler with no check; `n/a` = modifier chord or non-text key. `altgr_ok`: `yes` = the branch has `!e.altKey`; `no` = Ctrl+key branch with no altKey guard.

## Single place where shortcuts are defined

There is **no single table** for Slides. There is no `shortcuts.ts` and no help dialog (Docs has both: `apps/docs/src/renderer/shortcuts.ts`, `ShortcutsDialog.tsx`; grep of `apps/slides/src` for `ShortcutsDialog|Keyboard Shortcuts` finds nothing). The nearest to a registry:

- `apps/slides/src/renderer/keyboard-actions.ts` `handleGlobalKeydown` (one `window` keydown, attached once at `App.tsx:1202-1205`): all editing-mode shortcuts, one big if-chain with `e.key`.
- `apps/slides/src/renderer/show-keys.ts` `reduceShowKey` (`NAV_KEYS`, `SCREEN_KEYS`): slide show + presenter view only.
- `apps/slides/src/main/slides-main.ts:2035-2116` `buildSlidesMenu`: File/Edit/View accelerators, which send `slides:menu` commands to `App.tsx:2490-2531`.

## Structural findings

1. **Duplicate registrations (menu accelerator + renderer keydown)** for Undo/Redo, Cut/Copy/Paste, Print, Zoom in/out/reset (and Select all via role). The renderer comment (`keyboard-actions.ts:136`) calls its own undo a "fallback"; `keyboard-actions.ts:119` says the renderer sees Cmd+M before the menu accelerator "(measured)". Which layer wins per OS was not exercised here. The two paths are not identical: menu zoom goes through `previewZoom` (`App.tsx:2507-2509`), the keyboard path through `ctx.setZoom` (`keyboard-actions.ts:206-220`).
2. **Ctrl+Y redo and Ctrl+Shift+Z**: Ctrl+Y exists only in the renderer; menu has only Shift+CmdOrCtrl+Z.
3. **Open/Save/Save As** exist only as menu accelerators in the desktop; the web frame re-implements the same keys in `web/modules/slides/web-slides-api.ts:857-870` (capture-phase, `preventDefault` before the capability checks). Print is renderer-bound (`keyboard-actions.ts:164`) and the shared print accelerator is deliberately not installed for slides (`web/docs/bridge/print-accelerator.ts:5-6`).
4. **Keys forwarded frame -> host:** only Escape, through `installEscapeForwarder` (`web/docs/bridge/escape-forwarder.ts:34-60`, installed by `web/docs/bridge/module-bridge.ts:230`), which does check IME (`isComposing`, `keyCode===229`). Slides' own Esc handlers are spread across many places; they stay out of the forwarder's way via `defaultPrevented` and `[data-esc-local]`/dialog roles, plus `esc-overlay.ts` (`useEscOverlay`) which exists because the global handler is attached first and cannot see later preventDefaults (`esc-overlay.ts:1-4`).
5. **Navigation key lists copied in 4 places:** `show-keys.ts` NAV_KEYS (used by SlideShowView + PresenterView), `AudienceView.tsx:192-212`, reading view `App.tsx:2277-2296`, and slide rail logic in `keyboard-actions.ts:342-381`. Audience and reading copies lack Home/End/B/W/digits. `reduceShowKey` ignores modifiers entirely (Ctrl/Alt+Right etc. also advance). PowerPoint's show keys N/P/Backspace/A/=/S/E/Ctrl+P etc. are not in the table.
6. **Layer-order hazards:** global handler bails out for text fields (`inTextField`, `keyboard-actions.ts:25-28`) and edit overlay (`editing`); Esc priority is encoded as an ordered chain (`:229-286`). Capture-phase listeners (reading view, show, context menu, PrintDialog, Ribbon popovers) run before it.
7. **Layout-dependent matching:** whole Slides keymap uses `e.key` (lower-cased); no `e.code` except the shared ribbon-collapse helper. Shift+`.`/`,` fallbacks for font ladder are the only layout accommodation (`keyboard-actions.ts:55-56`). Zoom keys have no `!altKey` guard (AltGr+`=` on some layouts could fire); chords with `!e.altKey` are AltGr-safe.
8. **IME:** the global handler never checks `isComposing`; it relies on `inTextField()`/`editing`. TextEditOverlay's Esc/F2/Enter/Tab/Shift+Enter (`TextEditOverlay.tsx:914-960`) have no composition check; AI composer/popover/queue card and Comments Esc do.
9. **M365 conflicts visible while reading:** Ctrl+K opens the AI ask popover (PowerPoint: hyperlink); Ctrl+Enter in the overlay uses `e.ctrlKey` only (Control, not Cmd, on mac); F2 commits the edit; Cmd+Enter on mac starts the show from the current slide; no Ctrl+H, Ctrl+Shift+F/ Ctrl+Alt shortcuts, no Alt+F5/F7 etc. found.
10. **Hints are not derived from handlers.** Ribbon screentips are i18n strings with mac glyphs rewritten by `platformShortcuts` (`packages/i18n/src/index.ts:137-159`, applied in `createI18n` at `:219`); New Slide chord is hard-coded twice (`RibbonHomeTab.tsx:445`, `RibbonInsertTab.tsx:110`); File-menu hints in `Ribbon.tsx:1791,1802,1813,1847` are literal "Ctrl+…" (no mac form); context-menu hints are per-item literals (`context-menu-items.ts`). Only `ribbon-collapse.tsx` keeps handler and hint in one module (separate constant `RIBBON_TOGGLE_SHORTCUT`, line 30).
11. `packages/ui/src/ribbon-collapse.tsx:353-365` registers Ctrl+F1 / Option+Cmd+R (ribbon collapse); the compact-ribbon chord there is dormant in slides.
12. **Not found / out of slice:** no `before-input-event`, `globalShortcut`, or `registerCommand` in `apps/slides/src/main` or `preload`. `apps/shell` (the tabbed Electron host with its own File-menu accelerators, `apps/shell/src/main/index.ts:5895+`, `close-tab-chord.ts`) was only grepped, not inventoried here. packages/pptx-* contain no keyboard code (grep `keydown|KeyboardEvent` in packages/pptx-ops, pptx-render, pptx-engine: no matches).
